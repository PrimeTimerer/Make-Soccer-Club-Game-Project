## 1. 원칙

YKTK3 지침서 1장의 12개 원칙은 그대로 유효했다. 사카츠쿠에서 더한 것은 아래 9개다.

1. **같은 런타임의 성공 포트부터 본다.** 이틀 동안 ps3recomp의 옛 D3D12 백엔드를 하나씩 고쳤고, 경기에서 GPU TDR이 났다. GitHub의 Killzone 2/3 포트가 쓰는 live-draw 렌더러로 바꾸자 그날 경기가 열렸다. "검증된 렌더러 재사용"은 PS3에서도 첫 번째 규칙이다.
2. **베이스는 서브모듈로 고정하고 패치를 번호로 쌓는다.**
   - `ps3recomp`는 v0.18.0(4e8f3ca)에 고정했다. 런타임 수정은 `patches/00NN-*.patch` 25개(0001–0026, 0020은 없음)다.
   - 패치에는 서브모듈 파일만 넣는다. 저장소 파일(main.cpp 등)이 섞이자 `git apply`가 0015부터 통째로 실패했다. 깨끗한 체크아웃에 순서대로 적용해 작업 중인 서브모듈과 같은지 확인한다.
   - 리프트 결과(`recompiled/`)에 넣은 훅은 `patches/recompiled-00NN-*.patch` 23개다. 다시 리프트하면 다시 적용한다.
3. **모든 변경에 끄는 스위치를 단다.** 기본 동작을 바꾸는 수정도 환경 변수 하나로 예전 동작이 돌아오게 한다(`LD_PIPELINE=0`, `LD_DEPTH_RESOLVE=0`, `SAKA_PPU_DECODE=0` 등). A/B 비교와 롤백이 1분이 된다.
4. **진단은 opt-in.** 진단 코드는 남겨 두되 기본은 끈다. 게이트 파일(파일이 있는 동안만 기록)로 원하는 순간만 잡는다.
5. **결과가 같은지는 같은 경기 시각의 화면으로 본다.** 60fps 변경마다 같은 장면을 30틱 원본과 비교했다(전반 17:30, 4번 와타나베, 벨벳패스 Lv2). 경기 결과가 바뀌지 않았다는 증거다.
6. **치트는 게임 안에서 유지되는지까지 본다.** 메모리에 값이 써지는 것과 게임이 그 값을 쓰는 것은 다르다(돈 HUD, 시설 상한, 연습 이벤트). 그래서 값을 바꾸고 읽는 게임 함수 쪽에 훅을 단다.
7. **사용자 팀은 사본마다 따로 찾는다.** 같은 팀이 원본 클럽(0x00EE2934), 경기 팀 객체(0x00F8F158 + t×0x43C4), 경기 엔진 엔트리에 각각 있고 순서가 다르다. 원정 경기에서 엔진 순서가 뒤집혀 팀 스킬 무한이 안 됐다. 사본마다 포인터를 따라 소유 클럽을 확인한다. 정규 시즌, 컵, 시뮬레이션 경기도 따로 본다.
8. **게임 함수를 건너뛰고 데이터를 직접 쓸 때는 그 함수를 끝까지 읽는다.** 연습 칸을 직접 채웠더니, 배정 함수가 같이 만드는 보고 기록이 비어 이벤트와 결과가 나오지 않았다. 함수가 세팅하는 것을 전부 같이 넣는다.
9. **실행 중인 게임을 보호한다.** 주인이 게임을 켜 둔 동안은 `.new.exe`와 별도 작업 폴더(세이브 사본)로 테스트한다. 실행 중인 exe는 바꾸지 않는다. 어떤 빌드가 주인 게임인지는 프로세스 시작 시각으로 확인한다(벤치를 주인 게임으로 잘못 보고한 적이 있음).

## 2. 시작: 덤프·도구·폴더

첫날 목표는 "내 디스크의 EBOOT로 리프트·빌드하고 뭐라도 화면에 뜨는 것"이다. 사카츠쿠는 첫날 타이틀 화면까지 갔다.

1. **입력을 고정하고 기록한다.**
   - 디스크(ISO)와 업데이트 PKG를 준비한다.
   - EBOOT는 1.03 PKG에서 꺼내 복호화했다(`tools\ps3\ps3pkg_extract.py`, `self_decrypt.py`). Sony 키를 쓰므로 git에서 뺀다.
   - sha256을 적어 둔다(EBOOT `a5144796…`).
   - 실행 기준(버전, VFS, DLC 여부)을 문서로 먼저 정한다: `docs\PORT_1.03_RUNTIME.md`.
   - RPCS3에서 1.03 부팅 로그를 한 번(11분) 떠서 정답 순서로 썼다(BootCheck → ContentPermit → PatchCheck → …).
2. **펌웨어 모듈.**
   - 본인 PS3 펌웨어(4.93)의 libsre와 libspurs_jq `.sprx`를 복호화해 LLE로 리프트했다(`lift_prx.py` → `prx_src/<m>/`).
   - 실행 때 exe가 읽는 것은 재배치 이미지 `game\firmware\libsre_image.bin`, `libspurs_jq_image.bin`이다(`SAKA_PRX_DIR`로 바꿀 수 있음).
   - ps3recomp HLE에 없는 SPURS v2 API 8개는 HLE로 새로 만드는 대신 LLE로 풀었다.
3. **리프트.**
   ```
   .venv\Scripts\python -X utf8 ps3recomp\tools\ppu_loader.py game\EBOOT.ELF -o out\                    (2초)
   .venv\Scripts\python -X utf8 ps3recomp\tools\ppu_lifter.py game\EBOOT.ELF --functions out\EBOOT.functions.json ^
       --hle-stubs out\EBOOT.imports.json --output recompiled\ --chunk-lines 100000                      (약 2분)
   ```
   - 결과: OPD 12,433개, 리프트 함수 31,859개, 펌웨어 import 332개(28 라이브러리), C++ 105청크.
   - 파이썬은 항상 `-X utf8`로 실행한다. cp949 기본값이 리프터를 깨뜨린다.
4. **빌드는 처음부터 Release로 한다** (`build_release.bat`: clang-cl, Ninja, `-j 16`).
   - CMake 기본값이 Debug라 처음엔 -O0에 D3D12 디버그 레이어까지 켜져 16–20fps였다.
   - 풀 리빌드 3.6분, 증분 1–2분이 걸린다.
   - `PORT_SPU_INPUTS`에 EBOOT, PRX 두 개, CRI SPU 잡 ELF를 넣어 SPU 이미지도 리프트한다.
5. **폴더 규칙.** 한 폴더(`Desktop\Sakatsuku_Port`)에 다 담는다.
   - `game\`: EBOOT.ELF, dev_bdvd, dev_hdd0, firmware, `mods\korean`(한글 오버레이)
   - `gamedata\`: 세이브
   - `docs\`: 실행 기준, 지침서
   - `originals\`: ISO, PKG, 한글패치 exe
   - `tools\ps3\`: 복호화 스크립트
   - `tools\bench\`: 벤치와 픽스처 (4장)
   - 게임 데이터, 키, 원본, 게임 데이터에서 만든 한글 파일은 git에서 뺀다.
6. **분석 도구.**
   - REA MCP는 PowerPC ELF를 거부한다. 대신 REA에 들어 있는 Ghidra 12.1.4를 헤드리스로 직접 돌린다(`re\ghidra`). 언어는 `PowerPC:BE:64:A2ALT-32addr`이다. ALT가 아니면 VMX 코드가 잘린다.
   - 전체 디컴파일을 `re\decomp_all.c`(21 MB) 하나로 떠 두고 grep으로 찾는 것이 가장 빨랐다. 넓은 분석은 읽기 전용 Sonnet 에이전트에 맡기고, 막힌 부분만 직접 했다.
   - 바이트 검색과 임베디드 ELF 찾기는 REA rizin으로 한다.
7. **비교 기준.** RPCS3는 로그와 동작 참고용으로만 쓴다(큐브맵 정렬처럼 형식 규칙은 RPCS3 소스로 확인). 포트는 규칙을 직접 구현한다.
8. **자료 모으기.**
   - Vita판 치트(PCSG00198.psv, .suprx)와 5ch·바이두 치트 스레드를 모았다. 메모리 레이아웃이 PS3판과 같아서(Vita = PS3 + 0x80D1C300) 치트 변환의 지름길이 됐다.
   - 실존 모델 선수·감독 목록은 팬 사이트에서 대조했다(GAME-CMR 모델 목록, サカつく2013日記). 웹은 Scrapling을 쓰고, Shift_JIS/EUC-JP 페이지는 curl로 읽는다.

## 3. 진행 단계

단계는 "화면이 뜨는가 → 맞게 뜨는가 → 소리 → 빠른가 → 원래 속도 60fps → 즐길 기능 → 배포 → 주인 피드백 반영" 순서다. 완료 기준을 만족하면 바로 다음 단계로 넘어간다.

1. **Phase 0 셋업.** ps3recomp `templates/project`에서 CMakeLists, main.cpp, stubs.cpp를 가져온다.
   - 완료: 리프트와 빌드 성공, 60초 숨김 실행 로그.
2. **Phase 1 부팅.** 타이틀까지.
   - SPURS v2 API 미구현 → 펌웨어 libsre/libspurs_jq LLE.
   - cellGame 1.03(PARAM.SFO를 안 읽고 PatchCheck가 없음) → `stubs.cpp saka_register_patch_boot()`.
   - 게임이 등록되지 않은 1280x720 표면(0x00F00000)에 그린다 → `RT_DISPLAY_BY_SIZE=1`.
   - 매 프레임 RSX 명령을 만드는 SPU 태스크가 인터프리터로 돈다 → 리프트 이미지를 검증된 영역으로 등록.
3. **Phase 2 메뉴·세이브.**
   - 이름 입력이 검은 화면이었다. 원인은 세 가지였다.
     - OSK가 SDK에 없는 Init을 요구했다.
     - cellL10n NID 3개가 없었다. 이름은 NID 해시(SHA-1)로 찾았다.
     - SDL RAWINPUT이 USER 핸들 10,000개를 고갈시켰다(CreateWindowExW 오류 1158).
   - cellSaveData의 기본 매핑이 HDD0 루트를 무시했다.
   - DualSense가 안 잡혔다. Windows에서 SDL2가 빌드되지 않아서였다(패치 0001).
4. **Phase 3 3D 정확성.** 대표 3D 장면(경기, 얼굴 편집)이 RPCS3와 같이 보이면 완료.
   - FXC 동기 컴파일로 3D 장면이 멈췄다 → 셰이더 디스크 캐시.
   - 텍스처 유닛 13을 쓰는데 0–3만 바인딩했다 → 16유닛.
   - 프리미티브 리스타트를 해석하지 않아 머리가 가시 모양이 됐다.
   - VP 분기 베이스를 설정하지 않았다.
   - 경기에서 TDR이 났다 → live-draw로 교체.
   - 2x2 슈퍼샘플 표면의 축소 resolve를 버리고 있었다 → 대상 표면을 찾아 resolve. 이것으로 경기와 얼굴이 처음 화면에 나왔다.
   - 릴리스 뒤 주인 스크린샷으로 찾은 것: 컷신 전체가 흐림(깊이 resolve), 머리카락 가장자리와 피부의 검은 점. 5장 표 12–13.
5. **Phase 4 소리.**
   - HLE→PRX 브리지가 9번째 이후 스택 인자를 넘기지 않아 CRI 잡 큐 생성이 실패했다.
   - 페이지 속성에 SPU 비트가 없었다.
   - 인터프리터로 도는 CRI 잡이 늦었다 → CRI SPU 잡 6개 리프트. 믹스가 비트 단위로 같았다.
   - 소리가 DualSense 스피커로 나갔다 → 패드 장치는 건너뛰고 다른 출력 장치를 고른다.
6. **Phase 5 성능 (30fps 안정).**
   - 로딩: 압축 해제가 SPU 인터프리터로 30.35 s 걸렸다 → 게임에 원래 있던 PPU 디코더 경로로 0.64 s.
   - 로더 펌프를 넣었다.
   - 부팅 로고를 빨리감기했다(타이틀 21.5 → 6.5 s).
   - 경기 21 → 30fps.
7. **Phase 6 원래 속도 60fps.** 방법은 6장.
8. **Phase 7 즐길 기능.** 런처, 치트, F2 메뉴, 배속, 한글패치 오버레이. 방법은 7–8장.
9. **Phase 8 배포.** 방법은 9장.
10. **Phase 9 주인 피드백 반영.** 주인 플레이 로그와 스크린샷을 받아 고친다. 순서: 주인 로그의 훅 카운터 → 호스트 픽스처 → 숨김 벤치 → 주인 라이브 확인(4장).

## 4. 디버깅 방법

PS3 포트에는 세이브 스테이트가 없다. PPU와 SPU가 네이티브 스레드라 상태를 저장할 수 없다. 그래서 재현 지점은 "주인 세이브 사본 + 파일 열기 신호로 진행하는 숨김 벤치"로 만든다. 그보다 빠른 두 단계가 앞에 있다.

1. **주인 로그부터 본다.** `logs\launcher\saka-<날짜>.log`는 주인이 실제로 플레이한 세션의 stderr다.
   - `[cheats] code switches used: ...` 줄이 훅마다 호출 수를 센다.
   - 긴 세션 내내 0인 카운터가 역분석보다 먼저 원인을 보여 줬다("hizo roll 0", F6 40번 눌렀는데 발동 1번).
2. **호스트 픽스처 (약 30초).** `tools\bench\test_nov14_cheats.c`는 `saka_hooks.c`를 포함한다.
   - `game\EBOOT.ELF` 세그먼트와 세이브 `MAINnn.DAT`(게임 RAM 0x00EE27A0부터)를 버퍼에 올리고, 그 위에서 치트 코드를 그대로 실행한다.
   - `build_nov14_test.bat`으로 빌드·실행한다. 코드가 cwd 기준으로 `cheats\...`를 쓰므로 빈 폴더에서 돌린다.
   - 게임이 부팅 때 채우는 표 두 개(팀컬러 순서, 포지션 마스크)는 테스트가 직접 채운다.
   - 같은 방식: `test_edit_players.c`, `test_club_names.cpp`, `test_pending_cheats.c`.
3. **숨김 벤치 (1.5–4분).** 세이브 사본, 자체 cwd, 치트 사본으로 돌린다.
   - `PS3_GAMEDATA_ROOT`로 세이브 사본을 쓰고, `PAD_FILE`로 닫힌 루프 입력을 넣는다.
   - 진행은 파일 열기 마커로 판단한다: `mainmenu.arch` = 사무실, `match_before_all.arch` = 라커룸, `3d/audience/audience.par` = 경기. 타이틀에서 경기까지 약 60–90초.
   - 메뉴 입력은 타이밍이 흔들린다(로드 대화상자 기본값 NO, 하프타임에 ○가 메뉴에 갇힘). 시간 대신 화면 신호(파일 열기, 드로 수)로 판단한다.
   - 스크립트는 `tools\bench\`에 있다(사용법은 그 폴더의 README). 작업 파일은 `logs\bench\`에 생긴다.
     - `matchbench.ps1`: 경기까지. `-Cwd`(별도 작업 폴더), `-Prep`(시작 전 준비 스크립트)
     - `weekmatchbench.ps1`: 사무실부터 라커룸까지 화면마다 샷(그 주의 이벤트), 슈퍼플레이마다 샷
     - `officebench.ps1`: 숨김 창에 F2를 보내 원하는 탭을 찍고, 메뉴를 단계마다 찍음
     - `menubench.ps1`: 임의 메뉴 경로(`-Steps "START;W10;D;O;DUMP:name"`), `-Exe`로 `.new.exe` 지정
4. **주인 라이브 확인.** 화면, 조작감, 벤치가 못 여는 화면은 주인에게 맡기고, 보지 못한 것은 "미확인"으로 보고한다.

그 밖의 방법:
- **한 줄 요약 로그.**
  - `[perf]`(1초마다): fps, draws, loader, present, gpu 대기
  - `[freeze]` 감시 스레드: 1.2초 동안 프레임이 없으면 모든 게스트 스레드의 lr을 찍는다.
  - `[slow]`: 20 ms 넘는 셰이더·PSO·텍스처 단계
- **게임 로직 찾기.**
  - 정적: `re\decomp_all.c`에서 grep한 뒤 호출자를 따라간다. 결과를 기록하는 함수에서 거꾸로 올라가는 것이 빨랐다(카드 판정, 연습 보고 기록).
  - 동적: `SAKA_WATCH`(하드웨어 쓰기 감시), `SAKA_MEM_DUMP_GATE`(메모리 덤프), `SAKA_POS_SCAN`(경기 틱에서만 바뀌는 float), `PPU_STEP_CENSUS`(매 틱 같은 증분으로 쓰이는 값의 순위).
  - 주의: 경기 중 15초마다 전체 메모리 덤프를 뜨면 경기 흐름이 바뀐다(컷신 뒤 라커룸으로 돌아감). 경기는 작은 범위 로그나 쓰기 감시로 본다.
- **그래픽 원인 찾기.** 드로 CSV(`RSX_DRAW_CSV` + 게이트), 표면 덤프(`LD_SURF_DUMP`), HLSL 덤프(`LD_HLSL_DUMP` + `LD_NO_PSO_LIBRARY=1`로 모든 셰이더를 덤프), 깊이 버퍼 주소를 읽는 텍스처(`LD_ZETA_TEX_LOG=1`). 컷신 흐림은 이 넷으로 찾았다.
- **호스트 프로파일.** `SAKA_HOST_SAMPLE`, `/MAP` 링커 맵, `tools\host_sample_report.py`로 리프트 함수 단위 점유율을 본다.
- **화면 캡처.**
  - F12: live 모드에서 0.6초 게이트를 열어 표면 PPM과 드로 CSV를 남긴다.
  - `LD_FRAME_DUMP_GATE`
  - `SAKA_SIMTICK_SHOT`: 같은 경기 틱의 화면
- **같은 결과 판정.** 같은 빌드도 실행마다 타이밍 클래스가 갈린다. 같은 빌드를 두 번 돌렸더니 422개 중 74개만 같았다.
  - 새 스캔을 이전 스캔 전부와 비교해 98% 이상 같은 클래스를 찾는다.
  - 클래스가 다른 실행끼리의 차이는 증거가 아니다.
- **훅 규칙.**
  - 리프트 코드의 훅은 원래 호출 뒤에 보존 레지스터(r25–r31) 값을 C 함수로 넘긴다.
  - 게스트 메모리는 빅 엔디언으로 읽고 쓴다(`ld_be32` / `st_be32`). 필드 폭은 디컴파일의 저장 명령(`stb`/`sth`/`stw`)으로 확인한다.
  - 판정 결과만 바꾸고 게임 흐름은 그대로 둔다. 게임 자체의 검사는 남긴다.
- **프로세스 정리.** 테스트는 숨김 + 무음(`PS3_MUTE=1`)으로 하고, 끝나면 exe를 종료한다. 주인이 실행 중인 exe와 같은 파일을 쓰지 않는다.
- **셸 주의(이 PC).** Bash heredoc에서 따옴표나 백슬래시가 든 텍스트가 여러 번 깨졌다. 그런 텍스트는 Write로 파일을 만들고 스크립트가 읽게 한다.

| 스위치 | 용도 |
| --- | --- |

## 5. 그래픽·성능

성능은 추측하지 말고 스레드별로 잰다. PS3 포트의 프레임은 세 종류의 스레드가 나눠서 만든다.
- 게임 메인 PPU 스레드
- 렌더(프레임 클럭) 스레드: FIFO 해석, D3D12 기록, present
- SPU 스레드

어느 쪽이 꽉 찼는지 먼저 본다. `[perf] wait: gpu=0`이면 GPU는 원인이 아니다. 경기가 21fps에서 60fps가 되고 화면이 맞게 된 순서는 아래와 같다.

| 단계 | 문제 | 해결 | 효과 |
| --- | --- | --- | --- |
| 1 | FXC 동기 컴파일로 3D 장면 정지 | 셰이더 디스크 캐시, 이후 `ID3D12PipelineLibrary` PSO 캐시 | 두 번째 실행부터 present 최대 751 → 7.5 ms |
| 2 | RSX 명령을 만드는 SPU 태스크가 인터프리터로 돎 | 태스크 텍스트를 검증된 리프트 영역으로 등록 | 프레임당 대기 25.3 → 4.4 ms |
| 3 | 로딩 압축 해제가 SPU 인터프리터 | 게임의 PPU 디코더 경로로 분기 | 30.35 → 0.64 s |
| 4 | 렌더 스레드의 해시, CPU resolve, 이중 present | 4레인 해시, GPU resolve 때 복사 생략, 프로그램 메모, present 1회 | 경기 21 → 27–30fps |
| 5 | vblank가 드레인에 밀려 몰아서 옴 | vblank 전용 타이머 스레드 | 경기 24–27 → 30fps |
| 6 | present가 GPU를 기다림 | 2프레임 파이프라이닝 | present 3.5–4.2 → 0.2–0.4 ms |
| 7 | 텍스처를 매 프레임 해시 | `MEM_WRITE_WATCH`로 바뀐 페이지만 다시 해시 | 해시 99.2% 생략, 누락 0 |
| 8 | 1–2초 정지 | 명령 링의 마지막 워드를 랩 JUMP용으로 남김 (`end = begin + size - 4`) | 정지 0 |
| 9 | 메인 스레드 VMX float가 28% | SSE2/FMA3 4레인 경로 (NaN이면 정확한 스칼라) | 28 → 10% |
| 10 | lwcond 대기가 Sleep(1) 폴링 | 시퀀스 + 조건 변수 | 60틱 경기 2,500–3,000 드로에서 50 → 60fps |
| 11 | 선수 입장 장면(5,100 드로) 42–45fps | 변환한 정점 영구 캐시 (쓰기 감시로 무효화, 128프레임마다 재검증) | 57–61fps, 불일치 0 |
| 12 | 경기 전·이벤트 컷신 전체가 흐림 | 피사계 심도가 읽는 축소 깊이(0x00B40000)를 GPU로 만듦: 깊이의 R32F 스냅숏을 RGBA8 표면에 셰이더가 기대하는 바이트 순서로 그림 (패치 0024) | 경기장 샷 선명, 일반 플레이 변화 없음 |
| 13 | 머리카락 가장자리, 피부의 검은 점 | alpha-to-coverage를 RSX 샘플 격자대로, 폴리곤 깊이 바이어스를 D3D12에 전달, 스위즐 큐브맵 면을 128바이트로 정렬 (패치 0026) | 두 헤어스타일에서 머리카락·피부 깨끗 |

- **12번의 교훈.** 깊이는 GPU에만 있는데 NV3089 축소 블릿에 GPU 경로가 없어서, 낡은 게스트 바이트가 읽혔다. "화면 전체가 흐리다"는 셰이더 문제가 아니라 그 셰이더가 읽는 입력 표면 문제였다.
- **13번의 교훈.** 큐브맵 면 간격을 빈틈없이 붙여 계산해 패딩을 읽고 있었다. 형식 규칙은 RPCS3 소스(`TextureUtils.cpp`)로 확인했고, NaN 대체 같은 임시 셰이더 우회는 남기지 않았다.
- **효과가 없던 것도 남긴다.** D3D12 중복 상태 캐시(이득 0, opt-in으로 남김), usleep→FIFO 킥.
- **화질.** 스왑체인은 1280x720 고정이다. 업스케일은 아직 없다. 고주사율 모니터용 `LD_SYNC_INTERVAL=auto`는 opt-in이다.
- **남은 것.**
  - 3,300–3,800 드로와 장면 전환에서 49–57fps로 떨어지는 순간이 있다. 정점 캐시 조회(프레임당 2.5–4.6 ms)를 프레임 단위로 묶으면 줄어든다.
  - 태스크셋 정책 핸드오프 때문에 sl_decoder 태스크 리프트가 아직 부팅을 멈춘다.

## 6. 원래 속도로 60fps (고정 스텝 게임)

PS3 게임 상당수는 vblank 간격(SetInterval 2)으로 30틱이 고정돼 있다. 렌더만 60으로 올리면(`SAKA_FPS=60`) 게임 전체가 2배속이 된다. 그래서 먼저 게임 루프의 유형을 가른다. 기준은 RPCS3 60fps 패치 2,298개를 조사한 결과다.

- **A형** 실제 경과 시간으로 진행한다 → 리미터만 제거(Fight Night Champion).
- **B형** vblank 기준으로 진행한다 → vblank 120Hz와 작은 수정.
- **C형** 고정 스텝이다 → 틱당 증분을 전부 보정(켄잔, 사카츠쿠).

사카츠쿠는 C형이었고, 아래 순서로 풀었다.

1. **`SAKA_LOGIC60`.** SetInterval(2)를 1로 바꾸고, 프레임 루프의 대기도 간격 1로 했다. 여기서 모든 것이 2배속이 된다.
2. **`PPU_STEP_CENSUS`.** 매 틱 같은 증분을 쓰는 함수 42개를 순위로 뽑았다.
3. **엔진 타이머.** 엔진에는 켄잔식 비율이 이미 있었다. `this[0xC0]`가 틱당 vblank 수이고, dt 함수를 21곳에서 부른다. 이것을 1로 바꾸고 최소 측정 시간을 16,667 µs로 했다. 메뉴와 연출이 원래 속도로 돌아왔다.
4. **경기 시뮬레이션은 30Hz로 유지했다** (주인 선택: 결과 동일).
   - 경기 틱 `func_001F65AC`는 홀수 틱에 건너뛴다.
   - 실행하는 틱에는 타이머를 30Hz 값으로 보여 준 뒤 되돌린다.
5. **선수 동작.** 뼈 행렬(float 53,046개)이 여전히 30Hz로 끊겼다.
   - 행렬 외삽은 세 번 실패했다. 행렬이 매 프레임 다시 써졌고, 경기 상태를 외삽하자 게임 흐름이 바뀌었다.
   - REA로 선수 모델 업데이트를 찾아, 애니메이션 시간 게터만 반 스텝 앞의 값을 돌려주게 했다(`SAKA_ANIM60`).
   - 게스트 메모리에는 쓰지 않으므로 경기 결과는 그대로다.
6. **공.** 그려지는 위치 벡터(vr29)만 반 스텝 앞으로 보낸다(`SAKA_BALL60`). 땅 아래로는 보내지 않는다.
   - 착지 뒤의 순간이동을 지수적으로 미끄러지게 했더니 공이 선수보다 늦게 따라왔다(주인 지적). 이제 한 번의 튐은 경기 틱 하나 동안만 나눠 그린다(`SAKA_BALL_SMOOTH`, `long`은 예전 방식).
7. **검증.** 같은 경기 틱의 화면과 메모리 스캔을 비교했다. 전반이 75.9 s로 원본 74.5 s의 98%이고, 평균 58.5–59.7fps다.

교훈: 위치 값을 직접 바꾸면 흐름이 바뀐다. 결과를 보존하는 가장 작은 개입은 게임이 읽는 "시간"을 표시 프레임에서만 앞당기는 것이었다. 표시 보정은 짧을수록 좋다(한 틱 안에서 끝낸다).

## 7. 치트·인게임 UI

### 7.1 출발점과 형식

1. **다른 판의 치트를 출발점으로.**
   - PS3판 치트는 없었다. Vita판(VitaCheat .psv 37개, 능력치 편집 플러그인 .suprx)이 있었다.
   - 메모리 레이아웃이 같아서(Vita = PS3 + 0x80D1C300) 35개 중 29개를 바로 변환했다(`tools\psv_to_ps3.py`).
   - 엔디언을 주의한다. u16 두 개를 묶은 32비트 쓰기는 반쪽 순서를 바꾼다. u32 ID의 하위 16비트를 쓰는 코드는 주소에 +2를 한다.
   - 원 출처(바이두, 5ch)를 찾아 .psv에서 손상된 코드(UHODO, 유학 스텝)를 고쳤다.
2. **레이아웃이 같은 복사본을 주의한다.** 첫 로스터 검색은 상대 클럽의 로스터(0x00F9353C)를 찾았다. 값으로 찾은 주소는 다른 화면이나 ID로 한 번 더 확인한다.
3. **데이터 코드와 코드 스위치.**
   - 데이터 코드는 VitaCheat 문법 그대로 초당 10번 쓴다. `$CT00`/`$DT0x`는 메모리 값이 더 클 때만 쓴다(빈 칸 0은 그대로).
   - 판정을 바꿔야 하는 치트는 `$F0nn` 스위치로 만든다. 리프트 코드에 넣은 훅이 스위치가 켜졌을 때만 작동한다(`saka_hooks.c`, `recompiled-*.patch`). 32개 중 26번까지 쓰고 있다.
   - 스위치도 값을 가질 수 있다(`$F0nn 0 value`).
4. **고정, 한 번 쓰기, 갱신.**
   - 고정은 기본 꺼짐이다(주인 요청).
   - 한 번 쓰기 치트는 자기 설정이 바뀔 때만 다시 쓴다.
   - 설정은 세이브별로 저장한다(`cheats\saves\MAINnn\`: enabled, values, players, lists, training, staff, teamcolor). 어떤 세이브인지는 cellSaveData 파일 훅과 로스터 비교로 판정한다.

## 8. 한글화 (텍스트와 화면 그림)

원본 파일은 바꾸지 않는다. 한글은 모두 오버레이 폴더에서 읽는다.

1. **오버레이.** 한글패치 v0.8은 191개 파일의 XOR 델타다. 런처가 이것을 `game\mods\korean\data\`로 풀고, `PS3_USRDIR_OVERLAY`가 `USRDIR/` 경로를 그 폴더로 돌린다. 게임은 같은 파일을 bdvd와 hdd0 양쪽에서 읽으므로 오버레이는 둘 다 덮는다. 원본 사본 382개는 바뀌지 않았다.
2. **텍스트 다듬기.** `tools\korean_refine.py`가 오버레이의 문자열 1,253개(16개 파일)를 고친다.
   - 대상: 줄어든 선수 이름, 도쿄 베르디 선수단, J클럽 40개 이름, 용어 통일, 특성·팀컬러 이름, 비서 호칭.
   - `tools\korean_text.py`는 ID, 문자열 레코드 패딩, 아카이브 크기를 보존한다.
   - 텍스트 표는 99,359개 문자열 전부 끝났다(이름 필터 ng_word는 일부러 제외).
3. **세이브에 저장된 이름.** 클럽 이름 게터(0063C160)는 세이브의 UTF-16 이름을 그대로 돌려줘 번역을 우회한다. 저장된 이름이 그 클럽의 원래 이름과 정확히 같고 오버레이가 켜져 있을 때만 번역 이름을 보여 준다. 사용자가 바꾼 이름과 세이브 바이트는 그대로다.
4. **화면 그림.** `tools\korean_ui_labels.py`(프로젝트 .venv, Pillow).
   - 라벨 픽셀을 찾고, 배경을 복원하고(`inpaint`: 라벨 픽셀만 주변 배경 중앙값으로), 맑은 고딕 굵게로 그린다.
   - 바뀐 DXT5 4x4 블록만 다시 인코딩한다.
   - SLLZ 데이터가 칸보다 커지면 그 멤버를 PAR 끝으로 옮긴다(2 KB 정렬).
   - 라벨 크기는 옛 글자의 픽셀 상자가 아니라 **스프라이트 셀**로 정한다. 셀은 각 아카이브의 `NAME.sbs`(STSB)에 `u0, v0, u1, v1` float로 있다. 옛 상자에 맞추면 한 글자 단어가 아주 작아졌다.
   - 작업 순서: 블록 검출로 글자에 번호 → 스펙 파일 → `tools\korean_ui_moreN.py` 생성(배치마다 모듈 하나). 기울어진 배지·도장·세로 글자용 옵션(`rotate`, `disc`, `band`, `outline`, `shadow`, `squeeze`)이 있다.
   - 결과: UI 아카이브 약 90개, 텍스처 100장 이상, 라벨 1,100개 이상.
   - 남은 일본어: `edit_close`의 잡지 표지 3장, 작은 장식 글씨, 実行中 도장.
5. **함정.**
   - 기울인 글자를 RGBA 보간으로 그렸더니 거의 투명한 픽셀이 남아 DXT5 블록 전체가 빨갛게 됐다. 커버리지 마스크로 그리고 나중에 색을 칠한다. 바뀐 블록의 거의 투명한 픽셀에는 블록의 평균색을 준다.
   - 한글 파일은 게임 데이터에서 만든 것이라 저장소와 릴리스 zip에 넣지 않는다. 사용자는 런처에서 패치 exe로 설치한다.
6. **확인.** 미리보기 PNG(전·후)로 전부 보고, 벤치로 열 수 있는 화면은 게임 안에서 본다. 게임 안에서 못 연 화면은 그렇다고 적는다.

## 10. PS3 전용 체크리스트

PS3는 PPU 코드만 리프트해서는 끝나지 않는다. SPU(SPURS 태스크와 잡), RSX 명령 흐름, 펌웨어 모듈이 각각 따로 막힌다.

| 부품 | 포트에서 처리 | 확인할 것 (사카츠쿠 사례) |
| --- | --- | --- |
| PPU (Cell PowerPC 64, 빅 엔디언) | ppu_lifter → C++ 105청크 | "no continuation … halt" 경고 20개(텍스트 끝). VMX가 핫스팟일 수 있음 |
| SPU | 리프트 이미지 + 인터프리터 폴백 | SMC 감지 때문에 스트리밍되는 태스크·잡이 인터프리터로 떨어짐 → 지문(FNV) 확인 뒤 검증된 영역으로 등록 |
| SPURS | 펌웨어 libsre·libspurs_jq LLE | v2 API가 HLE에 없음. PRX 내보내기의 9번째 이후 스택 인자. 태스크셋 정책 핸드오프 |
| RSX | live-draw D3D12 | 등록 안 된 표시 표면, 슈퍼샘플 resolve, 깊이 resolve(GPU에만 있는 깊이), 프리미티브 리스타트, 텍스처 유닛 16, VP 분기, 명령 링 끝, FIFO 재동기, alpha-to-coverage, 큐브맵 면 정렬 |
| cellGame | stubs.cpp에서 래핑 | PARAM.SFO, PatchCheck, ContentPermit 경로 (RPCS3 실측 순서) |
| VFS·cellFs | `PS3_VFS_ROOT` / `PS3_HDD0_ROOT` / `PS3_USRDIR_OVERLAY` | 디스크는 읽기 전용, 패치는 쓰기 가능. 같은 파일을 bdvd와 hdd0 양쪽에서 읽음 (오버레이는 둘 다 덮어야 함) |
| cellSaveData | gamedata 루트 + 파일 훅 | 기본 매핑이 HDD0 루트를 무시. 세이브 = 게임 상태 RAM 0x00EE27A0부터 그대로 → 런처와 픽스처가 세이브를 직접 읽음. 확장 데이터는 세이브 옆 파일로 |
| 오디오 | cellAudio + CRI SPURS 잡 | 잡 리프트(JOBCRT 헤더 6개), 링이 비면 한 주기 대기, 패드 스피커 회피 |
| 패드 | XInput + SDL2 (DualSense) | Windows에서 SDL2 미빌드, RAWINPUT 핸들 누수 |
| OSK·L10n | 네이티브 입력 창 | Init 요구 제거, 없는 NID는 해시(SHA-1)로 이름 찾기 |
| 메모리 | 호스트 예약 | 페이지 속성(SPU 비트). PPU↔SPU 일관성 비용(초당 약 95만 쓰기) |
| 프레임 | 호스트 vblank 60Hz | 게임 로직이 프레임에 묶여 있는지 (6장) |
| 세이브 스테이트 | 불가 | 세이브 사본 + 입력 스크립트, 호스트 픽스처로 대신함 |

시작 체크리스트:

- [ ] 디스크와 업데이트 sha256 기록, EBOOT 복호화, 실행 기준 문서(버전, VFS, DLC)
- [ ] RPCS3로 목표 버전 부팅 로그 (호출 순서, 필요한 펌웨어 모듈 목록)
- [ ] import NID 목록과 ps3recomp HLE 비교 → 없는 것은 LLE나 HLE로
- [ ] EBOOT 안의 임베디드 ELF(SPU 태스크)와 잡 헤더 찾기 (REA rizin `/x 7f454c46010201`)
- [ ] 미들웨어 확인 (CRI ADX2 등). 오디오 잡은 리프트 대상
- [ ] Release 빌드부터 (Debug는 -O0에 디버그 레이어)
- [ ] 표시 버퍼 방식 확인 (등록하지 않은 표면에 그리는지)
- [ ] 세이브 저장·불러오기 1회, 세이브가 RAM 그대로인지 (그렇다면 픽스처가 쉬움)
- [ ] 대표 3D 장면(경기)까지 자동 벤치 경로와 세이브 사본
- [ ] 게임 루프가 프레임 고정인지 판정 (SetInterval, vblank 대기)
- [ ] 런타임 패치는 서브모듈 파일만, 깨끗한 체크아웃에 순서대로 적용되는지

## 11. YKTK3(PS2)와 다른 점

순서(1–4장)는 그대로 쓴다. 바뀌는 것은 베이스, 보조 프로세서, 재현 방법이다. 다른 콘솔 후보는 YKTK3 지침서 9장에 있다. 그 표의 PS3 칸은 이제 "ps3recomp + live-draw (사례: Killzone 2/3, inFAMOUS 2, 사카츠쿠)"로 채운다.

| 항목 | YKTK3 (PS2) | 사카츠쿠 (PS3) |
| --- | --- | --- |
| 베이스 | urban-reign-recomp (PS2Recomp + PCSX2 GS) | ps3recomp v0.18.0 + live-draw D3D12 |
| 코어 실행 | 런타임이 EE 하나를 스텝 | PPU 스레드 여러 개와 SPU 6개가 네이티브 스레드 |
| 보조 프로세서 | VU1 AOT | SPU 태스크·잡 리프트 + 검증된 영역 |
| 그래픽 | PCSX2 GS (업스케일 1x–8x) | RSX → D3D12 (1280x720 고정) |
| 빌드 시간 | 풀 빌드 35–50분 | 리프트 2분 + 풀 빌드 3.6분, 증분 1–2분 |
| 재현 지점 | 세이브 스테이트 | 세이브 사본 + 입력 스크립트, 호스트 픽스처 |
| 60fps | 원래 60 fields/s | 30틱 고정 게임 → 6장 |
| 치트 출처 | PCSX2 pnach | Vita판 VitaCheat (같은 레이아웃) |
| 분석 | REA rizin + capstone | REA의 Ghidra 헤드리스 (PowerPC A2ALT) 전체 디컴파일 |
| 인게임 메뉴 | pcsx2gs.dll UI 테이블 | live-draw present 직전의 ImGui DX12 |
| 한글화 | — | 오버레이 폴더(텍스트 + DXT5 UI 그림), 원본 무변경 |

## 12. 교훈과 피해야 할 패턴

| 피해야 할 것 | 실제 일 | 대신 할 것 |
| --- | --- | --- |
| 베이스의 낡은 경로를 고쳐 쓰기 | 옛 D3D12 백엔드를 이틀 고침 → 경기에서 TDR | 같은 런타임의 성공 포트가 쓰는 경로(live-draw)부터 |
| Debug 빌드로 성능 판단 | CMake 기본 Debug: -O0 + 디버그 레이어, 16–20fps | 처음부터 Release |
| 렌더만 60으로 | `SAKA_FPS=60` → 2배속 | 게임 루프 유형(A/B/C)을 판정한 뒤 시간 보정 |
| 결과 값 직접 외삽 | 경기 상태 float 외삽 → HUD가 사라지고 암전 | 게임이 읽는 시간을 표시 프레임에서만 앞당김 |
| 긴 표시 보정 | 공 튐을 여러 프레임에 걸쳐 미끄러지게 → 공이 선수보다 늦음 | 보정은 한 틱 안에서 끝냄 |
| 두 실행의 차이를 증거로 | 같은 빌드도 422개 중 74개만 같음 | 타이밍 클래스로 묶어 비교 |
| 경기 중 전체 메모리 덤프 | 15초 덤프가 경기 흐름을 바꿈 | 작은 범위 로그, 쓰기 감시 |
| 메모리 고정만 하는 치트 | 돈 HUD가 줄어든 값 표시, 시설 목록 깨짐 | 값을 바꾸는 함수 뒤의 훅, 마스터 데이터 수정 |
| 게임 함수 대신 데이터 직접 쓰기 | 연습 칸 고정: 보고 기록이 비어 결과·이벤트 없음 | 그 함수가 세팅하는 것까지 같이 |
| 필드 폭 짐작 | 秘蔵っ子 종류(byte)를 u32로 씀 → 다른 코스로 읽힘 | 디컴파일의 `stb`/`stw`로 확인 |
| 사용자 팀 = 객체 하나 | 원정 경기에서 엔진 팀 순서가 달라 무한 횟수 실패 | 사본마다 소유 클럽을 포인터로 따라가 판정 |
| 비슷한 검사를 하나만 풀기 | 외국인 정원: 라인업은 풀렸는데 월초 방출 요구가 남음 | 같은 메시지를 내는 함수를 전부 찾음 |
| int32 곱 그대로 | 관중 수 큰 값에서 수입이 넘침 | 64비트로 다시 계산 |
| 분석부터 시작 | (피했음) 주인 로그의 "hizo roll 0"이 원인을 바로 보여 줌 | 주인 로그의 훅 카운터부터 |
| 값 검색의 첫 결과를 믿기 | 상대 클럽 로스터에 치트를 씀 | 다른 화면이나 ID로 한 번 더 확인 |
| 엔디언을 그대로 두고 변환 | u16 두 개를 묶은 u32 쓰기 | 필드 폭과 순서를 확인하고 변환 |
| 패치에 저장소 파일 섞기 | 0015부터 `git apply`가 통째로 실패 | 서브모듈 파일만, 깨끗한 체크아웃에 순서대로 적용해 확인 |
| 옛 글자 상자에 한글 맞추기 | 한 글자 단어가 아주 작아짐 | .sbs 스프라이트 셀 크기 사용 |
| 기울인 글자를 RGBA 보간 | DXT5 블록이 빨갛게 | 마스크로 그리고 나중에 색칠 |
| 시각으로 정리할 파일 고르기 | 릴리스 exe가 휴지통으로 | 직전 목록의 이름으로 |
| 릴리스 안내문을 실제 실행 없이 쓰기 | 펌웨어 파일 이름이 틀린 채 배포됨 | 빈 폴더에서 zip으로 부팅 1회 |
| 예산을 넘겨 계속하기 | 정적 탐색 40분 예산 초과, 자세 외삽 세 번 실패 | 체크포인트에서 멈추고 주인에게 보고 |
| 벤치 스크립트를 세션 임시 폴더에 두기 | 세션이 바뀔 때마다 복사하고 고침 (11-09에 `tools\bench\`로 옮김) | 처음부터 한곳에 둔다 |
| 주인 실행 중에 exe 교체 | (피했음) | `.new.exe` + 별도 작업 폴더 |

한 줄 요약: 같은 런타임의 성공 포트 경로를 따르고, 주인 로그 → 호스트 픽스처 → 숨김 벤치 순으로 빠르게 확인하고, 결과를 바꾸지 않는 가장 작은 지점(시간, 판정 함수, 계산 입력)에 훅을 단다.
