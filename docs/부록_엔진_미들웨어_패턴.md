# 부록: 엔진·미들웨어 패턴 인덱스 (PS3)

Nov 14, 2026 · @PrimeTimerer · `리컴프_지침서.md`의 부록

같은 미들웨어나 같은 개발사 엔진을 쓰는 다른 게임을 만났을 때 바로 쓰려고, 사카츠쿠 PS3 포트에서 반복해서 나올 만한 패턴을 모았다. 각 패턴은 다음 순서로 적었다.
- 알아보는 법(시그니처)
- 증상
- 처리
- 사카츠쿠 증거

**확인**은 사카츠쿠에서 실측한 것이고, **추정**은 다른 게임에도 있으리라고 보는 것이다. 주소는 사카츠쿠 1.03 EBOOT 기준이라 다른 게임에서는 시그니처로 다시 찾는다. 공통 부품은 스타터 킷(`Desktop\PS3Recomp_StarterKit`)에 있다.

## 1. CRI ADX2 for PS3 오디오 (확인)

- **알아보는 법**
  - EBOOT 문자열에 `AtomDecoder`, `AsrVoice`, `DspPack1/2`, `DspPitchShifter`, `HcaMixer`가 있다. 사카츠쿠는 파일 0x97FBF0–0x9A7E20, Atom 1.30, AtomEx 1.27, ASR 1.03(2013년 4월 빌드)이다.
  - SPU 잡 프로그램은 `JOBCRT Ver14` 헤더로 시작한다. 사카츠쿠에는 6개가 있다: AtomDecoder 0x982E00, AsrVoice 0x992C80, DspPack1 0x99A080, DspPack2 0x99E280, DspPitchShifter 0x9A5700, HcaMixer 0x9B2E00.
  - libspurs_jq 워크로드 이름이 "CriAtom JobQueue"다.
  - 출력 경로: CRI Server Manager 스레드의 PCM 루프가 피드 함수를 포인터로 부르고(r4 = 6채널, r6 = 평면 float 포인터), cellAudio 링에 직접 memcpy한다. `cellAudioAddData`는 거의 안 부른다.
- **증상**
  - 무음: 잡 큐 생성이 실패한다(3번의 스택 인자, 페이지 속성).
  - 끊김: 인터프리터로 도는 잡이 늦는다(서버 주기가 25–36 ms까지 늦음).
  - 경기 중 정지: 소리를 기다리며 멈춘다.
- **처리**
  - 헤더로 잡을 찾아 ELF로 감싸 리프트한다. `tools/gen_cri_spu_jobs.py`가 base 0x7C00, entry 0x7C10으로 감싸고, 정책이 LS 0x7C00에 올려 +0x10으로 들어간다.
  - CRT는 스스로 재배치한다(`ila $r5,<table>`이 가리키는 단어: 헤더 +0x3C/+0x40, AtomDecoder 코덱 함수 표). 검증된 영역으로 등록할 때 비교에서 +0x3C..+0x5F를 뺀다. 다른 EBOOT면 지문 검사로 인터프리터로 돌아간다.
  - cellAudio 링이 비면 한 주기 기다리고(r−1 공개), 게임의 리드를 5 → 7로 올린다.
  - 컨트롤러 스피커 장치는 건너뛴다.
- **증거:** 서버 60 cycles/s, 무음 0%, 믹스가 인터프리터와 비트 단위로 같음(상관 1.000000).
- **다른 게임에서:** CRI를 쓰는 SEGA PS3 타이틀(VF5 등 ps3recomp 사례)에서 같은 헤더부터 찾는다. 버전이 다르면 헤더 오프셋을 다시 확인한다(추정).

## 2. SPURS v2, 태스크셋, 잡 큐 (확인)

- **알아보는 법**
  - ps3recomp HLE에 없는 NID 8개가 나온다: cellSpursInitializeWithAttribute2 0x30AA96C4, cellSpursAttributeEnableSystemWorkload 0x9DCBCB5D, _cellSpursTasksetAttribute2Initialize 0xC2ACDF43, cellSpursCreateTaskset2 0x4A6465E3, cellSpursCreateTask2WithBinInfo 0xE4944A1C, _cellSpursCreateJobQueueWithJobDescriptorPool 0x983BE7FC, _cellSpursJobQueuePort2CopyPushJobBody 0xC39173A4, cellSpursJobQueuePort2Sync 0xFACB3CED.
  - 메인 스레드가 `timer_usleep`에서 폴링한다.
  - EBOOT 안의 SPU 태스크 ELF는 REA rizin `/x 7f454c46010201`로 찾는다. 사카츠쿠에는 gs_task, sl_decoder, sl_lz_decode, sl_memcpy 4개가 있다.
- **처리**
  - 본인 펌웨어의 libsre와 libspurs_jq를 LLE로 리프트한다. 재배치 이미지 `game\firmware\<m>_image.bin`을 쓴다.
  - 매 프레임 RSX 명령을 만드는 태스크(gs_task)의 텍스트를 FNV-1a-64 지문 확인 뒤 검증된 영역으로 등록한다. SMC 감지 때문에 스트리밍되는 코드는 인터프리터로 떨어지기 때문이다.
- **미해결:** sl_decoder를 리프트하면 부팅이 멈춘다(정책 핸드오프). 해결은 정책도 검증된 영역으로 리프트하고 스택 리셋 PC를 등록하는 것이다(Yakuza 포트 방식).
- **증거:** 프레임당 RSX 대기 25.3 → 4.4 ms.

## 4. 프레임 고정 게임 루프 판별 (확인)

- **알아보는 법**
  - 초기화에서 `SetInterval(2)`를 한 번 부른다(사카츠쿠 0x00194500 → 0x0069BEE0, 1..10 제한).
  - 프레임 루프가 `count - last >= interval` vblank만 기다리고 경과 시간을 보정하지 않는다.
  - .rodata에 1/30, 1/60 상수가 없고 1.0f가 수천 개 있다(프레임 단위 스텝).
- **유형** (RPCS3 패치 2,298개 조사)
  - A형 리미터만 제거: Fight Night Champion "Unlock FPS" (blr + FPS cap 1000.0).
  - B형 vblank 120Hz + 작은 수정: JoJo, Army of Two, F1 CE, Iron Man.
  - C형 고정 스텝 전부 보정: 켄잔(약 220 KB 패치), 사카츠쿠.
- **처리 (C형)**
  - 간격을 1로 바꾼다.
  - `PPU_STEP_CENSUS`로 매 틱 같은 증분을 쓰는 함수의 순위를 낸다.
  - 엔진 타이머(5번)를 찾는다.
  - 결과가 중요한 시뮬레이션은 30Hz로 유지한다(6번).
- **함정:** 렌더만 60으로 올리면 2배속이다. 경과 시간 보정 없는 대기는 vblank를 2배로 해도 같다.

## 5. 켄잔식 엔진 타이머 (사카츠쿠 확인, SEGA 계열 추정)

- **알아보는 법** (사카츠쿠: 타이머 객체 `[0x00E93E70]`, 태스크 관리자 `func_00634CF8`가 매 틱 갱신)
  - `this[0xC0] = this[0xC8 + this[0xC4]*4]`: 틱당 vblank 수(보통 2), 모드 표에서.
  - dt 함수(`func_006352E8`, 21곳에서 부름): 실시간 모드(`this[0x14C]`)면 측정값 `this[0x150]`(33,333–100,000 µs로 제한), 아니면 `this[0xC0] / 60.0`.
  - 배율 표(사카츠쿠 0x00E93F74) `{0, 0.5, 1.0, 1.5, 2.0}`를 `this[0xC0]`로 골라 속도 3개와 그 제곱을 정한다.
  - 60.0f 상수(0x00EAEF88)를 타이머 모듈 함수 몇 개가 읽는다.
  - `PPU_STEP_CENSUS`에 `+0.0333333` float 스텝(실행 중 계산되는 dt = 1/30)이 보인다.
- **처리:** 60틱에서 `this[0xC0] = 1`, 측정 최소값 16,667 µs. 메뉴와 연출이 원래 속도로 돌아왔다(전반 48.1 s → 68.2 s, 원본 74.6 s. 나머지는 6번에서 해결).
- **RPCS3 켄잔 패치(Pakundo v1.7)와 같은 생각이다.** 비율 = 디스플레이 fps / 30을 전역에 두고 float 스텝은 나누고 정수 카운터는 비율 번째 프레임에만 움직인다. 사카츠쿠 엔진에는 이 비율이 이미 들어 있었다.
- **다른 게임에서:** SEGA PS3 타이틀(용과 같이 계열, 다른 스포츠 타이틀)은 먼저 이런 타이머 객체와 배율 표를 찾는다. 찾으면 C형 보정이 훨씬 작아진다(추정).

## 6. 30Hz 경기 시뮬레이션과 60Hz 표시 (확인)

- **알아보는 법**
  - 장면 태스크의 상태 머신(사카츠쿠 `func_0065DF60`, 상태 2/3/9)이 경기 틱(`func_001F65AC` → `func_00288948`)을 부른다.
  - 경기 엔진은 자체 고정 단위(+10, +225)를 쓰고 엔진 타이머를 쓰지 않는다.
  - 선수 포즈(뼈 행렬)가 경기 틱 안에서 계산되고 매 프레임 다시 써진다.
- **처리**
  - 경기 틱을 홀수 틱에 건너뛰고, 실행하는 틱에는 타이머를 30Hz 값으로 보여 준 뒤 되돌린다. 결과가 원본과 같다(같은 경기 시각에 같은 이벤트).
  - 움직임은 게임이 읽는 애니메이션 시간을 표시 프레임에서만 반 스텝 앞당긴다. 공은 그려지는 벡터만 반 스텝 앞으로 보내고, 튐 보정은 한 틱 안에서 끝낸다.
- **피할 것:** 행렬이나 경기 상태를 직접 외삽하면 덮어써지거나 게임 흐름이 바뀐다.

## 7. pxd 로더: 프레임당 한 단계 (사카츠쿠 확인)

- **알아보는 법**
  - 로그에 `pxd_lib initialize()`와 스레드 `pxd::async_file_access`가 있다.
  - 설치 표시 `USRDIR/pxd_installed.pib`, `install.pib`가 있다.
  - 관리자(0x005D59E4)가 매 프레임 로더 상태 머신(0x002E0030 / 6EE8 / 7AC8)을 부르고, 상태 9(비동기 완료 대기)는 프레임당 한 번만 본다.
- **증상:** 파일마다 33 ms 한 프레임. 콘솔 속도 그대로이지 포트가 느린 것이 아니다(RPCS3와 같은 속도로 측정됨).
- **처리:** 로더 펌프. 간접 호출 표를 래퍼로 바꿔 한 프레임 안에서 여러 단계를 돌린다(프레임당 15 ms 예산). 부팅 로고는 파일 마커 두 개 사이를 빨리감기한다.
- pxd를 누가 만들었는지(개발사 공용인지)는 확인하지 못했다. 같은 문자열이 보이는 게임에서 먼저 확인한다.

## 8. SLLZ 압축과 PPU 대체 경로 (사카츠쿠 확인)

- **알아보는 법:** 압축 파일이 `SLLZ`로 시작한다. 읽기 단계(`func_006DF39C`)가 SPU 태스크 sl_decoder에 보내는데, 같은 함수에 태스크셋이 없을 때 쓰는 PPU 디코더(`loc_006DF49C`)가 있다.
- **처리:** 리프트 코드에서 PPU 경로로 분기한다(`recompiled-0001`, `SAKA_PPU_DECODE=0`이면 원래대로). 읽기 단계 30.35 s → 0.64 s.
- **일반 교훈:** SPU 작업이 느리면 먼저 같은 함수 안에 PPU 대체 경로가 있는지 본다. 개발용·디버그용으로 남아 있는 경우가 많다(추정).

## 9. RSX 출력·resolve 패턴 (확인)

| 패턴 | 알아보는 법 | 처리 |
| --- | --- | --- |
| 등록 안 된 표면에 그림 | 플립하는 표면(0x00F00000)이 등록된 디스플레이 버퍼(0x0, 0x3C0000)와 다름 | live-draw가 현재 1280x720 대상을 표시. 옛 백엔드는 `RT_DISPLAY_BY_SIZE=1` |
| 2x2 슈퍼샘플 + 축소 resolve | 3D가 2560x1440 표면에 그려지고 아무 텍스처도 그것을 읽지 않음. NV3089 축소 블릿이 타일 2개(1022 + 258 px)로 1280x720에 복사 | 표시 버퍼가 아닌 대상도 live 표면을 찾아 GPU로 resolve |
| 깊이 resolve (피사계 심도) | 깊이(zeta)를 반 크기로 블릿(타일 2044 + 516)한 뒤 A8R8G8B8 + remap 0xAA93으로 읽음 | 깊이의 R32F 스냅숏을 RGBA8 표면에 셰이더가 기대하는 바이트 순서(R = 23-16, G = 15-8, B = 7-0)로 그림 |
| 그림자 맵 | 3D 셰이더가 텍스처 유닛 13에서 PCF 샘플 | 유닛 16개 바인딩 |
| GPU가 쓴 스키닝 팔레트로 보이는 것 | 선수가 바인드 포즈 X자 | 사카츠쿠에서는 VTF가 원인이 아니었다(1D 정점 텍스처 지원만 추가). 3D가 이상하면 먼저 위의 resolve 누락을 확인한다 |

## 10. RSX 형식 함정 (확인)

- **프리미티브 리스타트:** 인덱스 TRIANGLE_STRIP이 0xFFFF로 끊기고, 한 BEGIN/END 안에서 256개 단위 배치로 나뉜다. 해석하지 않으면 얼굴이 가시가 된다.
- **VP 분기:** BRA/BRI/CAL 대상은 절대 슬롯이다. 분기 베이스와 비트를 설정하지 않으면 정점마다 루프를 돌아 GPU TDR이 난다.
- **명령 링 끝:** `end = begin + size - 4`(랩 JUMP 자리). 사카츠쿠는 링 바로 뒤에 프래그먼트 프로그램을 두고 상수를 제자리에서 고쳐서, 끝까지 차면 JUMP가 덮여 1–2초 정지했다.
- **스위즐 큐브맵:** 면 사이 간격은 128바이트 정렬이다. 빈틈없이 붙이면 패딩을 읽어 피부에 검은 점이 생긴다(RPCS3 `TextureUtils.cpp`).
- **머리카락:** alpha-to-coverage는 RSX 샘플 격자대로, 폴리곤 깊이 바이어스는 D3D12까지 전달한다.
- **셰이더 컴파일:** FXC가 동기라 첫 장면이 멈춘다. 디스크 캐시와 PSO 라이브러리, VS는 최적화를 생략한다.

## 11. 세이브 = RAM 블록 (사카츠쿠 확인)

- **알아보는 법:** 세이브 파일을 RAM 덤프와 비교한다. 사카츠쿠 `MAINnn.DAT`(706,988바이트)는 RAM 0x00EE27A0..0x00F8F14C와 바이트 단위로 같다.
- **쓰임**
  - 런처가 게임 없이 세이브를 읽는다(선수 목록 등).
  - 호스트 픽스처가 세이브를 RAM 자리에 올려 훅을 실제 데이터로 돌린다(약 30초).
  - 세이브 형식을 바꾸지 않고 확장한다: 세이브 옆 파일(`MAINnn.DAT.edit3`)을 MAIN 파일 해시로 묶는다.
- **다른 게임에서:** 매니지먼트 게임은 이런 경우가 흔하다(추정). 첫 세이브 1회 때 비교해 본다.

## 12. 다른 플랫폼판과 같은 메모리 레이아웃 (사카츠쿠 확인)

- **알아보는 법:** 다른 판(사카츠쿠: PS Vita PCSG00198)의 치트 주소와 PS3 RAM의 같은 값을 맞춰 본다. 사카츠쿠는 Vita = PS3 + 0x80D1C300(돈 0x00EE2844 = Vita 0x81BFEB44)이다.
- **처리:** 그 판의 치트를 상수로 옮긴다(35개 중 29개). 엔디언 주의: u16 두 개를 묶은 쓰기는 반쪽을 바꾸고, u32 하위 16비트 쓰기는 주소 +2로 한다.
- **예외:** 초기화된 데이터 테이블(선수 마스터)은 판마다 배치가 달라 바이트 오프셋을 그대로 못 쓴다. 힙 주소 치트도 안 맞는다.

## 13. 마스터 테이블 포인터 배열 (사카츠쿠 확인)

- **알아보는 법:** `FUN_00574270(id)`가 포인터 배열 0x008D4A9C[id]를 돌려주고, 각 헤더가 `+0 count, +4 records`다. 표는 EBOOT의 정적 데이터다.
  - 예: 0x2B 클럽하우스 시설 41 × 0x14, 0x2A 경기장 시설 50 × 0x10, 0x27 플레이스타일 67 × 0x3C, 0x94 스킬 표, 0x43 경기장 수용, 0x54 각성 게이지.
- **쓰임**
  - 치트가 결과 대신 마스터 값을 바꾼다(시설 크기 0).
  - 픽스처가 EBOOT만 올려도 표를 읽는다.
  - 마스터를 쓰는 치트는 게임을 다시 시작하면 원래대로 돌아온다.

## 14. 경기 이벤트 기록과 이월되는 결정 (사카츠쿠 확인)

- **알아보는 법**
  - 플레이 시퀀스(코어 DB 표 0x10)의 기록이 0x38D8바이트 링이다.
  - 플레이 빌더(`func_00205220`, `func_00205568`)가 템플릿에서 새 기록을 만든다.
  - 파울 이벤트(record+0x28)의 코드가 이전 기록에서 넘어온다(`[prev+0x223C + 0xCC]`).
  - 코드 % 3: 0 없음, 1 옐로, 2 레드. 코드 / 3: 파울 종류.
  - 경기 결과는 경기 중에 쓰이지 않고 끝날 때 복사된다.
- **처리:** 판정을 바꾸려면 기록이 만들어진 직후(빌더 반환 뒤)에 그 코드를 바꾼다. 결과 표나 표시 쪽은 늦다.
- **찾는 법:** 결과 기록 함수에서 거꾸로 올라간다(`re\decomp_all.c` grep → 호출자).

## 15. 같은 팀의 여러 사본 (사카츠쿠 확인)

| 사본 | 사카츠쿠 위치 | 우리 팀 판정 |
| --- | --- | --- |
| 원본 클럽 | 0x00EE2934 (로스터 0x00EE2954) | 클럽 ID 0x100 또는 u32 0x00EE28AC |
| 경기 팀 객체 | 0x00F8F158 + t × 0x43C4 | +0 클럽 |
| 경기 엔진 엔트리 | match + 0x334 + t × 0x126C (`func_00208AE8`) | +4 팀 데이터 → +8 경기 팀 객체 → +0 클럽 (킥오프 훅이 기록) |
| 경기 데이터 (진영) | 진영 X = `[[core3+0x10]+0x50]`, 하프마다 뒤바뀜 | 진영 → 팀 → 클럽 |

- 엔진 엔트리의 순서는 홈/원정에 따라 경기 팀 객체와 다르다. 고정 슬롯으로 판정하면 원정에서 틀린다.
- 시뮬레이션 경기(결과만)와 다른 클럽끼리의 경기도 같은 함수를 지나므로, 치트는 우리 클럽인지 확인한다.

## 16. 보고 기록을 같이 만드는 배정 함수 (사카츠쿠 확인)

- **알아보는 법:** 주간 처리(`func_005177A0`)가 결과와 이벤트를 줄 때 칸 데이터가 아니라 별도 보고 기록의 선수 ID를 본다. 배정 함수(`func_00511F50` 등)가 칸과 보고 기록을 함께 만든다.
- **증상:** 치트로 칸만 채우면 계획은 끝나는데 결과·이벤트가 없다. 주인 로그의 훅 카운터가 0이었다.
- **처리:** 주간 처리 직전에 배정 함수가 남겼을 보고 기록을 만들어 준다. 필드 폭은 디컴파일의 `stb`/`stw`로 확인한다(종류는 byte).
- **일반 교훈:** 게임 함수를 건너뛰는 치트는 그 함수가 세팅하는 것을 끝까지 읽는다.

## 17. UI 그림 아카이브 (사카츠쿠 확인)

- **알아보는 법**
  - 화면 아카이브 `sb*/NAME.par` 안에 DDS(DXT5)와 레이아웃 `NAME.sbs`(매직 `STSB`)가 있다.
  - 멤버는 SLLZ로 압축된다.
  - 셀은 `u0, v0, u1, v1` 리틀 엔디언 float(픽셀 / 텍스처 크기)다.
- **처리:** 바뀐 4x4 DXT5 블록만 다시 인코딩한다. 커진 멤버는 PAR 끝으로 옮긴다(2 KB 정렬). 라벨 크기는 셀로 정한다(`tools\korean_ui_labels.py`, `tools\saka_par.py`).
- **함정:** 기울인 글자를 RGBA로 보간하면 거의 투명한 픽셀 때문에 블록이 빨갛게 된다. 마스크로 그리고 나중에 색칠한다.

## 같은 계열 게임을 만나면

1. EBOOT 문자열 검색: `JOBCRT`, `Atom`, `pxd`, `SLLZ`, `STSB`. 무엇이 있는지로 1·7·8·17번을 바로 고른다.
2. import NID 목록: 2·3번의 미해결 NID가 있으면 LLE와 패치부터 한다.
3. 게임 루프: `SetInterval`과 60.0f를 읽는 타이머 객체를 찾는다(4·5번).
4. 세이브와 RAM 비교, 다른 판 치트와 비교(11·12번)로 치트와 픽스처의 지름길을 확인한다.
5. 스포츠 게임이면 결과 기록 함수부터 거꾸로 올라가고(14번), 팀 사본표(15번)를 먼저 만든다.
